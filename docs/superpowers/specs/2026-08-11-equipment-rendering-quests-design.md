# Equipment Rendering and Admin Quest Design

## Goal

Make equipped inventory render consistently in the admin dashboard and game avatar, make Tas equipment tabs and items interactive without double-active glow, and allow admins to create quests that appear, progress, and reward inside the game.

## Existing constraints

The backend is Python stdlib in `emulator/emulator.py` with JSON persistence in `emulator/data/db.json`. Avatar previews are generated by `emulator/avatar_render.py`. The ActionScript client reads static mission definitions from `missiondefine` XML, then requests per-user state through `GameMember.getMission` and claims rewards through `GameMember.getMissionPrize`.

## Equipment contract

`onlyID` identifies one inventory record. `position=1` means equipped and `slot` identifies its body slot. The backend will normalize duplicate records and use the same supported slot/type mapping for `memBody`, avatar preview, and admin display. Equipment actions will update the authoritative user goods record and body mapping atomically before returning the refreshed goods/body state.

## UI behavior

Tas owns one active category at a time. Selecting a tab first clears the selected/glow state on all sibling tabs, then activates only the requested tab. Each item card is a single clickable control with selected styling; selecting it opens its detail/action state. Equip/unequip requests refresh the list and character preview from the backend, preventing stale duplicate cards.

## Quest contract

The database receives a `quests` collection for admin-created definitions and per-user quest progress. Each quest has an id, name, description, category/type, action code, optional target type/frame, target count, level requirement, and reward fields. The backend exposes quest definitions/state through the same game HTTP gateway used by the existing client and validates reward claims server-side, including one-time claim protection.

The client will preserve built-in mission definitions and add a dynamic mission conversion path for admin-created definitions returned by the server. Dynamic missions use the existing action-code progress hooks and existing mission dialog/reward flow, so newly created quests render in the existing Tugas menu and can be completed without manually editing the bundled XML.

## Admin behavior

The user detail view renders `/avatar_img?uid=<id>` from normalized equipped goods. Equipment chips and catalog cards expose clear click actions for equip/unequip/delete. A Quest editor lists existing quests, supports create/edit/delete, and exposes the fields needed by the game contract. Saving reloads the shared state and updates the count and relation views.

## Testing and acceptance

Tests cover equipment normalization, slot mapping, avatar gear composition, item action persistence, tab exclusivity, quest CRUD, quest progress, and single-use rewards. Manual acceptance verifies: an equipped item appears in the avatar and correct inventory category; clicking Tas tabs leaves exactly one glow; clicking/equipping an item updates the avatar; an admin-created quest appears in-game after refresh; its target advances from a matching game action; and its reward can be claimed only once.
